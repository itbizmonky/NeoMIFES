**発行日:** 2026-08-04
**対象時点:** Phase 8f / Phase 7y 完了時点 (`23c2cc2`、ローカルコミット済み・push 未実施)
**位置づけ:** 本書は [`master_roadmap.md`](master_roadmap.md) と同格の **Plan-of-Record 補遺**である。roadmap v2.0 が規定した「何を作るか」に対し、本書は **「作ったつもりで作られていないもの」** を実コードの検証によって特定し、Phase 再編の根拠を与える。

## 1. エグゼクティブサマリ

### 1.1 結論

**NeoMIFES は現時点で「テキストエディタ」ではなく「テキストエディタ用エンジン群 + 動作するデモシェル」である。**

8 フェーズ・約 35,000 行・966 テストを積み上げ、エンジン層 (Document / Rendering / Search / Encoding / Syntax / Plugin) は**いずれも商用水準に達している**。一方で、**アプリケーションとして成立するために不可欠な機能群が、ロードマップ上にフェーズを一度も割り当てられないまま今日に至っている。**

最も端的な事実:

> **NeoMIFES は編集したファイルを保存できない。**
> 製品コード全体で `CreateFileW` の呼び出しは 1 箇所 (`src/platform/src/file_mapping.cpp:13`、mmap 用の**読み取り専用**オープン) のみ。`saveFile()` / `WriteFile` / `ofstream` による文書書き出しは**一切存在しない**。

これは実装漏れではなく、**ロードマップの構造的欠陥**の帰結である (§6)。

### 1.2 数値サマリ

| 観点 | 状態 |
|---|---|
| エンジン層の完成度 | **高い** — 10GB mmap / 60fps / 100万 Undo / 22言語ハイライト / RE2 検索、いずれも DoD 実測達成 |
| アプリケーションシェルの完成度 | **ほぼゼロ** — 保存・開く・タブ・メニュー・設定・IME・状態表示のいずれも未実装 |
| 要件定義書 §6「必須機能・編集」の充足率 | 22 項目中 **13 項目未達** (§3.2 参照) |
| roadmap §12.3 出荷判定チェックリスト 22 項目 | 達成 **4**、未着手 **18** |
| 「設定システムが無いため縮退した」と文書に明記された設計判断 | **13 箇所** (§5.2) |
| 商用出荷までに必要な新規フェーズ | **3 フェーズ** (8.5 / 8.6 / 12 の再定義) |

### 1.3 一行での評価

**技術的野心と実装品質は世界水準。ただし「製品」として見たときのロードマップの優先順位づけが根本的に誤っており、直ちに是正が必要。**

## 2. 検証方法

本書の全ての主張は **実コードに対する機械的検証**に基づく (CLAUDE.md 絶対ルール 3: 推測実装をしない / 推測記述をしない)。記憶・過去のドキュメント記述を根拠にした箇所は一つも無い。

実施した検証:

```bash
# 保存経路の全数調査
grep -rn "saveFile|WriteFile|ofstream|CreateFileW" --include=*.h --include=*.cpp src/ include/

# アプリケーションシェル要素の存在確認
grep -rn "CreateMenu|LoadMenu|HACCEL|GetOpenFileName|IFileDialog|STATUSCLASSNAME" --include=*.cpp src/
grep -rn "TabBar|DocumentManager|Settings|isDirty|recentFiles|WM_HSCROLL|WM_CONTEXTMENU" --include=*.h --include=*.cpp src/

# メインウィンドウが処理するメッセージの全数列挙
grep -n "case WM_" src/ui/src/main_window.cpp

# 配布物リソースの存在確認
find . -name "*.rc" -o -name "*.ico" -o -name "*.manifest" | grep -v build
```

各節の主張には、この検証で得られた具体的な file:line を付す。

## 3. P0 — 出荷不能ギャップ (製品として成立しない)

> **P0 の定義:** これが 1 つでも残っている限り、いかなる形態でもエンドユーザーに配布してはならない項目。

### 3.1 P0-1: ファイル保存機能が存在しない 🔴 最重大

**事実:**
- `src/` 配下に文書をファイルへ書き出すコードは存在しない
- `CreateFileW` の唯一の呼び出しは `src/platform/src/file_mapping.cpp:13`、`GENERIC_READ` のみ
- ファイル書き込みを行う唯一のコードは開発用計装 (`src/app/frame_profile.cpp:43`、`src/app/startup_profile.cpp:7`) と検索履歴永続化 (`core::SearchHistory::saveTo`) の 3 箇所で、いずれも文書とは無関係
- `Ctrl+S` のキーハンドラは存在しない (`src/app/main.cpp` の Ctrl 系ハンドラは `Ctrl+F` / `Ctrl+Shift+P` / `Ctrl+Shift+F` / `Ctrl+G` の 4 つのみ)
- コマンドパレット登録コマンド 10 件 (`main.cpp:1356-1420`) にファイル操作系は 1 件も無い

**影響:** ユーザーが行った全ての編集は、プロセス終了時に無言で失われる。**編集内容を失うソフトウェアは、いかなる意味でもテキストエディタではない。**

**波及する未実装機能:** 保存経路が無いため、以下も自動的に不可能:
- 文字コード変更 (要件定義書 §6)、改行コード変更 (同)、BOM 切替 (同) — いずれも「変換して保存」が本体
- 自動保存 (要件定義書 §6・§15)、バックアップ (同)
- 未保存変更の警告 (`isDirty` フラグ自体が `Document` に存在しない)

**設計上の追加論点:** 10GB ファイルを mmap で読み取り専用オープンしている以上、**同一ファイルへの上書き保存は自明ではない** (自身がマップしているファイルへの書き込み)。一時ファイル + `ReplaceFileW` によるアトミック置換と、その前段でのマップ解放が必要。これは Phase 6d の mmap 設計が保存を考慮せずに確定したことの帰結であり、**Phase 8.5 で最初に解く必要のある設計課題**である。

### 3.2 P0-2: ファイルを開く手段がコマンドライン引数しかない 🔴

**事実:**
- `GetOpenFileNameW` / `IFileOpenDialog` の呼び出しはゼロ
- 起動時の `--open <path>` のみがファイル指定手段
- 実行時にファイルを開く経路は Grep 結果クリック (`Ctrl+Shift+F`) と タグジャンプ (`F12`) の 2 つだけ — いずれも**既に検索でヒットしたファイル**にしか到達できない
- `Ctrl+N` (新規)、`Ctrl+O` (開く)、ドラッグ&ドロップ (`WM_DROPFILES`) いずれも未実装

**影響:** ユーザーは「エディタを起動してから、編集したいファイルを選ぶ」という、テキストエディタの最も基本的な操作ができない。

### 3.3 P0-3: 複数ファイルを同時に扱えない 🔴

**事実:**
- `TabBar` / `DocumentManager` 相当のクラスは存在しない
- `src/app/main.cpp` は `document::Document` を単一のローカル変数として保持し、`openDocumentAt()` は**それを move-assign で破壊的に置き換える**
- 要件定義書 §6 が「複数タブ」「複数ウィンドウ」を**必須機能**として明記

**影響:** ファイル A を見ながらファイル B を編集する、という開発者の基本作業ができない。Grep 結果からジャンプすると**編集中の文書が警告なく破棄される** (P0-1 と複合し、データ損失に直結)。

### 3.4 P0-4: メインエディタが IME を処理しない 🔴 (日本語市場では致命的)

**事実:**
- `src/ui/src/main_window.cpp` が処理する Windows メッセージは 15 種 (`WM_PAINT`/`WM_SIZE`/`WM_DPICHANGED`/`WM_KEYDOWN`/`WM_SYSKEYDOWN`/`WM_CHAR`/`WM_MOUSEWHEEL`/`WM_LBUTTONDOWN`/`WM_MOUSEMOVE`/`WM_LBUTTONUP`/`WM_COMMAND`/`WM_NOTIFY`/`WM_ERASEBKGND`/`WM_CLOSE`/`WM_DESTROY`) — **`WM_IME_*` は 1 つも含まれない**
- `ImmGetContext` / `CANDIDATEFORM` / `COMPOSITIONFORM` の使用はゼロ
- IME を扱っているのは Find bar / Grep bar / コマンドパレット / 桁ジャンプバーの 4 つのみ。これらは標準 `WC_EDIT` 子コントロールであり、**IME を Win32 から無償で得ているだけ**でメインの D2D 描画テキスト領域とは無関係

**影響:** メインエディタでの日本語入力は、確定文字列が `WM_CHAR` で届くため「入力自体は成立する」が、
- **変換中の未確定文字列がインライン表示されない** (どこに何を入力しているか見えない)
- **変換候補ウィンドウがキャレット位置に追従しない** (画面の隅に出る)

秀丸 / MIFES を「凌駕する」と掲げ、roadmap §16.1 で CJK IME を専用節として規定しながら、**日本語がまともに打てない**状態にある。これは日本語市場向け製品として単独で出荷を阻む。

### 3.5 P0-5: 配布物としての体裁が皆無 🔴

**事実:**
- `.rc` リソーススクリプト、`.ico` アイコン、`.manifest` のいずれも**リポジトリに 1 つも存在しない**
- メニューバーが無い (`CreateMenu` / `LoadMenuW` の呼び出しゼロ)
- アクセラレータテーブルが無い (`HACCEL` ゼロ) — 全キーバインドが `editor_input.cpp` / `main.cpp` にハードコードされた `if` の連鎖
- ステータスバーが無い (`STATUSCLASSNAME` ゼロ) — カーソル位置・文字コード・改行コード・行数のいずれも画面に出ない
- ウィンドウタイトルにファイル名が反映されない
- 右クリックコンテキストメニューが無い (`WM_CONTEXTMENU` / `TrackPopupMenu` ゼロ)

**影響:** 起動しても「どのファイルを開いているのか」「今どこにカーソルがあるのか」が画面から一切分からない。exe のアイコンは MSVC 既定のまま。**現状のバイナリを配布した場合、ユーザーは製品と認識しない。**

## 4. P1 — 商用品質を満たさないギャップ

### 4.1 P1-1: 設定システムが存在しない

**事実:** 設定の読み書き機構は皆無。フォント・タブ幅・テーマ・キーバインド・全て C++ 定数としてハードコード。

**特筆すべき二次被害:** 「設定システムが存在しないため」という理由で**機能を縮退させた設計判断が、文書上に 13 箇所記録されている**。実例:

| 箇所 | 縮退内容 |
|---|---|
| roadmap §3.7 (4b8d) | タブ幅を 4 固定。`Auto` モード (文書統計から多数派採用) を断念 |
| roadmap §3.7 (4b8f) | クリップボード分配ルールの選択肢を断念 |
| roadmap §5.5 (5c3) | 秀丸互換 Grep 結果ペインを MVP へ縮退 |
| detailed_design §10.x | `kTabWidth=4` を `render_pipeline.cpp` と `main.cpp` に**二重定義**、手動同期を「既知のトレードオフとして受容」 |

**評価:** 設定システムの欠落は単独の欠陥ではなく、**後続フェーズ全ての設計を継続的に劣化させ続ける負債**として既に作用している。定数の二重定義という具体的な技術的負債まで発生している。P1 の中では最優先。

### 4.2 P1-2: 基本編集操作の欠落

| 機能 | 状態 | 根拠 |
|---|---|---|
| `Ctrl+A` 全選択 | ❌ 未実装 | `main.cpp` の Ctrl ハンドラに `'A'` 無し |
| 自動インデント | ❌ 未実装 | `autoIndent` の実装ゼロ。**ただし 60機能マトリクスは「Phase 4b8」と記載、その 4b8 は「保留項目なし」で完了宣言済み** (§6.3 の文書整合性欠陥) |
| 横スクロール | ❌ 未実装 | `WM_HSCROLL` / `leftColumn` 相当ゼロ。長い行の右端は**到達不能** |
| スクロールバー | ❌ 未実装 | ミニマップが代替しているが、Windows 標準の操作感を提供しない |
| 縦編集 | ❌ 未実装 | マトリクスは「4b8 (研究)」、実施記録なし |

**特に横スクロールの欠落は重大:** 画面幅を超える行の内容を**見ることも編集することもできない**。ミニマップは縦方向のみを扱う。

### 4.3 P1-3: `main.cpp` の肥大化 (アーキテクチャ負債)

**事実:** `src/app/main.cpp` は **2,053 行**。CLAUDE.md 絶対ルール 4 は「1 関数 ≤ 50 行、1 クラス ≤ 300 行」を定めているが、`main.cpp` はクラスですらないため形式上ルールを免れたまま、実質的にアプリケーション全体の状態機械・全キーバインド・全モード遷移・全ウィジェット配線を単一ファイルに蓄積している。

**評価:** タブ (複数文書)・設定・メニューを追加した時点で、このファイルは確実に破綻する。Phase 8.5 は**機能追加であると同時に `main.cpp` の解体である**必要がある。

### 4.4 P1-4: 大規模文書の増分解析 DoD 未達 (既知・追跡中)

roadmap §7.11 の DoD「1 文字入力後の増分解析 ≤ 50ms」は、50 万行文書で約 **155.95ms** のまま未達。Phase 7q → 7t → 7u (revert) → tree-sitter 内部調査 の 4 回の挑戦を経て、`docs/issues/tree_sitter_incremental_parse_cost.md` に「tree-sitter の `ts_parser_parse()` アーキテクチャの構造的限界」と結論済み。

**評価:** 技術的判断としては正しく、調査の質も高い。ただし**優先順位として誤っている** — 「50 万行のファイルで 100ms 速くする」ことに 4 フェーズを費やす一方、「ファイルを保存する」に 0 フェーズしか費やしていない。これは §6 の構造的原因が最も鮮明に表れた事例である。

**提言:** 本項目は **P2 へ格下げし、Phase 12 直前まで凍結**する。DoD 値そのものを「50 万行文書では 200ms を許容する」と改訂することも選択肢として明記する (未達を放置するのではなく、達成不能と判明した目標を正直に改訂する)。

## 5. 良好な点 (維持すべき資産)

批判的分析が本書の主目的だが、**維持すべき強みを明示しないレビューは有害**なので併記する。

### 5.1 エンジン層の品質は世界水準

| 領域 | 実測 DoD | 評価 |
|---|---|---|
| 起動時間 | 148ms (目標 300ms) | ✅ 2 倍のマージン |
| Document Engine | Piece Tree + mmap + Lazy Decode、10GB 対応 | ✅ VSCode 同等以上 |
| Rendering | avgFrame ≈ 16.5ms (60fps) | ✅ 達成 |
| Undo | 100 万件実測 | ✅ 達成 |
| シンタックス | 22 言語 / tree-sitter | ✅ 秀丸・サクラを大きく凌駕 |
| 検索 | RE2 + 複数行 + Grep | ✅ 商用水準 |

### 5.2 開発規律は極めて高い

- **ADR 21 本** — 全ての重要判断に理由が残っている
- **966 テスト** (単体 58 ファイル / 統合 11 / ベンチ 7) — Debug / Release / UBSan の 3 構成で全 green
- **実機 probe による検証文化** — tree-sitter のノード型を記憶で書かず、毎回使い捨て probe で実測してから実装する規律が Phase 7a 以来一貫している
- **失敗の正直な記録** — Phase 7u を「実装完了後に全面 revert」と記録し、DoD 未達を「未達」と書き続けている。これは非常に稀で価値が高い

**これらは商用開発組織の水準を上回っている。**§6 の問題は規律の欠如ではなく、**規律が向けられた方向の誤り**である。

## 6. 構造的原因分析 — なぜ保存機能が 8 フェーズ見落とされたのか

**単なる「うっかり」ではない。3 つの構造的原因が特定できる。**

### 6.1 原因 1: 設計書には存在した L6 が、簡略化された図とフェーズ表から脱落した

**重要な訂正 (本節は初稿から修正済み):** 当初「アプリケーションシェルはどの設計書にも存在しない」と分析したが、**これは誤りだった**。実ファイルを精査した結果、`basic_design.md` §2.1 のレイヤ構成は 7 層で定義されており、**必要なものは正しく規定されていた**:

```
L7: UI Shell        Win32 ウィンドウ, タブ, ダイアログ          ← タブ・ダイアログが明記
L6: Application     Command Dispatcher, Undo/Redo, Session      ← §3.2 で
                    ・Session Manager: ワークスペース状態の永続化 (JSON)
                    ・Config Manager:  ユーザー設定 (JSON/TOML) の読み書きと動的反映
L5: Editor Core / L4: Rendering / L3: Domain Engines / L2: Plugin Host / L1: Platform
```

**では何が起きたのか — 文書チェーンの劣化である:**

| 段階 | 状態 |
|---|---|
| 要件定義書 §6 | 「複数タブ」「自動保存」「履歴」を**必須機能として明記** ✅ |
| `basic_design.md` §2.1 / §3.2 | **L7 にタブ・ダイアログ、L6 に Session Manager・Config Manager を規定** ✅ |
| **CLAUDE.md §3 の簡略レイヤ図** | **L6 (Application) が丸ごと脱落。** `UI Shell → Editor Core → Rendering → Document → Search/Encoding → Plugin → AI` の 7 段で、Session/Config が消えた ❌ |
| roadmap §2 フェーズ表 | **CLAUDE.md の簡略図に 1:1 対応する形でフェーズを切った**ため、脱落した L6 にはフェーズが割り当てられなかった ❌ |
| 実装 | L6 相当は `src/app/` に存在するが、中身は `document_open` / `editor_input` / 各種 bridge のみ。**Session Manager も Config Manager も無い** ❌ |

**教訓:** 上位文書を要約して下位の作業計画を作るとき、**要約で落ちた項目は永久に実装されない**。CLAUDE.md §3 の図は「毎セッション必ず読まれる」ため実質的に最も影響力のある設計図であり、そこから L6 が消えたことが決定的だった。

**是正:** CLAUDE.md §3 のレイヤ図に L6 (Application Shell) を復活させる (本レビューで実施済み)。

### 6.2 原因 2: 「必須機能」が非フェーズの章へ退避された

60 機能継承マトリクス (roadmap §1.5) を精査すると、**Phase 番号ではなく「§13.5」のような UI/UX 方針章を参照している行が複数ある**:

| 機能 | マトリクスの「対応 Phase」欄 | 実態 |
|---|---|---|
| タブ UI (複数ファイル) | **§13.5** | §13.5 は方針章であり、フェーズではない |
| 分割ビュー | **§13.5** | 同上 |
| タブグループ・ピン留め | **§13.5** | 同上 |
| Zen mode | **§13.5** | 同上 |
| ステータスバー | 「Phase 3+」 | 「+」が指すフェーズは存在しない |
| 自動保存・バックアップ | **Phase 12** | Phase 12 は「総合品質保証・出荷判定」。機能実装フェーズではない (カテゴリエラー) |
| 履歴 (最近開いたファイル) | **Phase 12** | 同上 |

**「章番号を書くこと」が「計画したこと」と誤認された。** 章はいつまでも実装されない。

そして **「ファイルを保存する」はマトリクスの 60 機能に一度も列挙されていない** — 三大エディタ全てが当然に備えているため、「継承すべき差分」として認識されなかった。

### 6.3 原因 3: 完了判定が「そのフェーズの計画」に閉じている

Phase 4b8 は §3.7 で「**roadmap 上の保留項目を残さず完全に完了**」と宣言されている。しかし 60 機能マトリクスは `自動インデント` と `縦編集` を Phase 4b8 に割り当てており、**いずれも実装されていない**。

完了判定が「そのフェーズのために書いた計画書」だけを見て行われ、「**プロダクト全体の要求に照らして何が残ったか**」を見ていない。同じ構図が全フェーズで繰り返された結果、各フェーズは全て「完了」でありながら製品は完成しない。

### 6.4 なぜ検知されなかったのか — 検証手段の偏り

CLAUDE.md §11 のセッション終了チェックリストは**ドキュメント間の整合性**に強く焦点を当てている (ADR と設計書の同期、RESUME_HERE の鮮度、TIMELINE への追記)。これは実際に多くの不整合を捕捉してきた。

しかし、**「製品として動くか」を人間の目で確認する手順が無い**。加えて、複数セッションにわたり自動化環境での GUI 操作 (修飾キー合成・スクリーンショット) が不調で、実アプリ確認が「プロセスが 3 秒後も生存していること」に縮退していた (`reference_no_win32_gui_automation.md`)。

> **プロセスが生きていることは、製品が使えることを意味しない。** `Ctrl+S` が何も起きないことは、生存確認では永久に発見できない。

### 7.4 改訂後の全体フェーズ順

```
[完了] Phase 0〜8f  エンジン層 + プラグイン基盤
   ↓
★ Phase 8.5  アプリケーションシェル      ← 最優先・P0 解消
   ↓
★ Phase 8.6  製品化基盤                  ← P1 解消
   ↓
  Phase 12'  MVP 出荷判定 (新設)          ← ここで一度「売れる状態」を作る
   ↓
  Phase 10   ログ解析 / CSV / JSON-XML    ← 最大の差別化点。AI より先
   ↓
  Phase 11   Git / LSP / マクロ
   ↓
  Phase 9    AI プラグイン
   ↓
  Phase 12   総合品質保証・正式出荷
```

**Phase 9 (AI) を後方へ移した理由:** roadmap は AI を Phase 9 に置いていたが、CLAUDE.md 自身が「**AI 機能は完全プラグイン化。エディタ本体は AI 無しでも 100% 動作しなければならない**」と定めている。本体が 100% 動作していない段階で AI を実装するのは、この原則と矛盾する。また AI 機能は外部 API 依存で陳腐化が速く、**本体が完成した後に実装した方が製品価値が高い**。

**Phase 10 (ログ解析) を前倒しした理由:** roadmap §1.5 が「**本ソフト最大の差別化点**」と位置づけており、AI と異なり自己完結し陳腐化しない。MVP 出荷後の最初の目玉機能として最適。

### 7.5 「Phase 12' MVP 出荷判定」の新設意義

現行 roadmap は Phase 12 (総合品質保証) を全機能実装後に 1 度だけ置いている。これは**最初の出荷が最も遠い未来になる**という計画上の欠陥を持つ。

Phase 8.6 完了時点で NeoMIFES は「**秀丸・サクラの代替として実用に耐え、22 言語のシンタックスハイライトと 10GB ファイル対応で明確に上回る**」状態に到達する。ここで一度出荷判定を通し、実ユーザーのフィードバックを Phase 10 以降へ反映する方が、製品として遥かに健全である。

**Phase 12' の DoD (Phase 12 のサブセット):**
- [ ] ファイルを開く / 編集する / 保存する / 名前を付けて保存する が全て動作
- [ ] 日本語 IME でインライン変換が正しく表示される
- [ ] 未保存で終了しようとすると警告が出る
- [ ] 10 個のファイルをタブで開いて相互に切り替えられる
- [ ] 設定でフォント・タブ幅・テーマを変更でき、再起動後も保持される
- [ ] Authenticode 署名 + Portable Zip 配布
- [ ] クラッシュ 0 (8 時間ソーク)
- [ ] 既存の全性能 DoD (起動 300ms / 60fps / 10GB) を維持
