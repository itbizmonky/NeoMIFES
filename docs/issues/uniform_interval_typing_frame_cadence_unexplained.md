# Issue: 一定間隔(20ms)でのキー入力注入時、メッセージキュー滞留が無いにも関わらずフレーム間隔が30〜32msに張り付く現象が未解明(P2 — 実害軽微、原因未調査)

- **起票日:** 2026-09-06(WI-32実装後の再検証中に発見)
- **対象:** 不明(`RenderDevice::endFrame()`のPresent1呼び出し、DXGIのプレゼンテーションキュー、DWM合成のいずれかと推定されるが未特定)
- **優先度:** P2(実際の人間のタイピングは瞬間的なバーストを含むため、WI-32の修正で実用上は解決している。本issueは純粋に技術的な未解明点の記録)

## 事実

WI-32(`docs/issues/keystroke_burst_render_backlog.md`参照)の検証中、`PeekMessageW(WM_KEYFIRST, WM_KEYLAST, PM_NOREMOVE)`が一度も「追加のキー入力がキューにある」を検知しない条件下(20ms間隔で1文字ずつ`PostMessage`注入)でも、修正の有無に関わらずフレーム開始間隔が一貫して30〜32ms(注入した20msではない)に張り付くことを実測で確認した。真のバースト(遅延なし一括投入)では`PeekMessageW`が正しく滞留を検知し、修正が設計通り再描画を合流させることは別途確認済み——本issueは「なぜキューに滞留が無いのに20msではなく30msというより長い間隔になるのか」という、キュー滞留とは独立した別の現象についてのもの。

## 未検証の仮説

- DXGIスワップチェーンの内部プレゼンテーションキュー(`IDXGISwapChain2::SetMaximumFrameLatency`等、本コードベースでは明示設定なし=デフォルト値)が、`Present1`呼び出し自体は高速に返しつつ、実際のバッファ確保が数フレーム遅延する形で間接的にこの間隔を作っている可能性。
- DWM合成側のスケジューリング(本コードベースは`WS_EX_NOREDIRECTIONBITMAP`を使用していないため、通常のDWM合成パスを経由する)が、この環境固有の何らかのタイミングを課している可能性。
- 本セッションで使用した外部プロセスからの`PostMessage`という入力注入手法自体が、実際のハードウェアキーボード入力とは異なるOSレベルの配送タイミングを持つ可能性(この場合、実機での実際のタイピングでは発生しない可能性がある)。

## 対応方針

現時点では対応不要と判断する。WI-32はこの現象自体を修正対象としておらず(修正対象は「メッセージキューの真の滞留」)、実際の人間のタイピングにおける体感改善は既に実証済み。本issueは技術的好奇心・将来のレンダリングパイプライン最適化検討時の参考情報として記録するのみ。
