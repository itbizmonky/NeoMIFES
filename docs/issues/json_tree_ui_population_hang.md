# Issue: JSON/XMLツリーUIが大規模ファイルでUIスレッドを長時間ハングさせる (P1 — 🟢 解決済み)

- **起票日:** 2026-08-30 (v1出荷判定、JSON/XML Treeモードの大規模ファイル実機検証中に発見)
- **解決日:** 2026-09-01 (v1出荷判定 🎉M5達成後、次フェーズ候補の実装優先度①として着手)
- **対象:** `src/ui/src/json_tree_pane.cpp`/`.h`(`ui::JsonTreePane`、WI-15c実装、WI-15hでXML側と共通化)
- **優先度:** P1 (実害は3分以上のUIハング、メモリ枯渇は伴わないため[decode_cache_unbounded_growth.md](decode_cache_unbounded_growth.md)より緊急度は低い)
- **対応 Phase:** 未定 (原因調査は未着手、実装のみで解決するか設計変更が必要かも未確定)

## 事実

v1出荷判定の「10GBファイル対応(JSON/XML Treeモード)」検証で、約100MB・145万要素のJSON配列ファイルを`--open`で開いた直後に「Toggle Structure Tree」コマンド(`view.jsonTree.toggle`)を実行してJSONツリーモードを有効化したところ、コマンド実行直後からプロセスが`Responding=False`(UIハング)になり、**168秒(約3分)経過してもハングが解消しなかった**ため、これ以上待たずに`taskkill`で強制終了した。

メモリは3.7GB前後で安定しており(こちらは[decode_cache_unbounded_growth.md](decode_cache_unbounded_growth.md)のようなOOMではない)、緊急停止が必要な危険な状態ではなかったが、実用に耐えないレベルの応答不能である。

## 推定原因 (❌ 誤りと判明、下記「実際の原因」参照)

`ui::JsonTreePane`(WI-15c実装)によるツリーアイテム構築、および`ui::JsonTreePane`自体への流し込み処理が、145万ノードに対して同期的・非仮想化(non-virtualized)な実装になっている可能性が高い。CSVモードの`CsvGridPane`が`WC_LISTVIEW`の仮想モード(`LVS_OWNERDATA`)を採用しているのに対し、`JsonTreePane`は「実際の`WC_LISTVIEW`アイテム」を使う設計だとメモリ内に記録されている(仮想モードではない) — これが真の原因である可能性が高いが、本issue起票時点では未検証。

**重要な設計上の関連性:** WI-15h(2026-08-25)で「`Ctrl+Shift+J`をJSON/XML両対応の単一トグルへ統一」しており、`ui::JsonTreePane`はJSON・XML共通のUI実装である。つまりこの問題はJSONツリーだけでなくXMLツリーモードにも同一のボトルネックとして存在する可能性が高い(未検証)。

## 実際の原因 (2026-09-01、標準プローブで実測・確認済み)

**着手前調査で、上記の推定原因は誤りだったと判明した。** `ui::JsonTreePane`が実際に使っているコントロールは`WC_TREEVIEW`(`SysTreeView32`)であり、`WC_LISTVIEW`ではない。Win32のTreeViewコントロールには、ListViewの`LVS_OWNERDATA`に相当する仮想モード機構がそもそも存在しない。

標準プローブ(`treeview_probe.cpp`、スクラッチパッドで`cl.exe`直接コンパイル)で、`TVM_INSERTITEMW`単体の挿入コストを実測した:
- `WM_SETREDRAW`未抑制時: 約100〜150マイクロ秒/件。145万件 × 130μs ≒ 188秒 — **報告された168秒の3分ハングとほぼ一致し、「大量の個別`SendMessageW`呼び出しそのものが支配的コストである」ことを裏付けた。**
- `TVI_LAST`と`TVI_FIRST`で有意差なし(現行comctl32はテール挿入をO(1)でキャッシュ済みと判断できる)。
- `WM_SETREDRAW`で描画抑制すると約4.7倍高速化(144.5μs→30.8μs/件)するが、145万件では単体でも概算45秒かかり、実用的な解決にはならない。

さらに、本issueの再現条件が「JSON**配列**ファイル」である点から、145万要素が**1階層に横並びのフラット配列**である可能性が高いと判断した。この場合、単純な「子ノードをクリックするまで生成しない遅延ロード」だけでは解決しない(ルート直下の1階層を展開した瞬間に145万件を一度に挿入することになり同じ問題が再発するため)。

## 実装した修正 (2026-09-01)

`ui::JsonTreePane::populateTree()`を、総ノード数のしきい値(`kEagerFullyExpandThreshold` = 20,000)で2経路に分岐する設計へ変更した:

1. **しきい値以下:** 従来通り全ノードを挿入し全展開(**動作は一切変更しない**)。ただし`WM_SETREDRAW`による描画抑制を新規追加(無条件の安全な高速化)。
2. **しきい値超過:** Win32標準の「子がまだ無くても展開グリフ`[+]`だけ出す」機構(`TVIF_CHILDREN`/`item.cChildren = 1`)を使い、実際にクリックして展開されるまで子ノードを一切挿入しない遅延ロードへ切り替える(`TVN_ITEMEXPANDINGW`通知をハンドルし、その場で1階層分だけ実子を挿入)。さらに、1階層あたりの実挿入数を`kMaxChildrenPerLevel`(5,000件)で上限を設け、超過分は「`… 他 N 件 (省略)`」という非展開の1行に集約する — フラット配列のような「1階層に大量の子」というケースにも対応するため。

この機構(`TVIF_CHILDREN`/`TVN_ITEMEXPANDINGW`)はこのコードベースで初採用のため、本番コード実装前にスクラッチパッドで別の標準プローブ(`treeview_lazy_probe.cpp`)を書き、実機で動作を確認してから着手した。副次的な発見: 一度実子が挿入されたノードは、再度折りたたんで再展開しても`TVN_ITEMEXPANDINGW`が再発火しない(comctl32が「既に実子がある」ことを自動的に認識するため)ことをプローブで確認 — 二重投入防止のための追加のブックキーピングは不要と判断した(念のため`TVM_GETNEXTITEM`/`TVGN_CHILD`による防御チェックは残した)。

## 実機検証結果 (2026-09-01、Release、実際にissueと同条件のファイルで再現)

issueと同条件(約74MB・145万要素のJSON配列ファイル)を生成し、実機で修正の効果を確認した。

**⚠️ 検証中に、本issueとは別の重大な発見があった:** この規模のJSONファイルを`--open`で開くだけで(JSON構造ツリー機能に一切触れなくても)、JSON構文ハイライトが原因と見られる約47秒のUIハングが発生することが判明した。同一内容を拡張子`.txt`(構文ハイライト対象外)で開くと約1秒で応答可能になることを確認し、原因を特定した。**これは`ui::JsonTreePane`とは無関係の別問題であり、本issueのスコープ外として`json_syntax_highlight_large_file_open_hang.md`(P1)へ新規起票した。**

この別問題の影響を避けるため、ドキュメントを開いて構文ハイライトが安定してから(有=47.3秒後)、構造ツリーのトグルコマンド自体の挙動を単独で計測した:

| 操作 | 修正前(推定) | 修正後(実測) |
|---|---|---|
| トグルコマンド自体の応答 | ハング(推定168秒〜) | **9ms**、即座に応答維持 |
| 非同期インデックス構築(バックグラウンド) | - | 4.4秒(UIスレッドは終始応答可能、`sawUnresponsive=False`) |
| インデックス完了直後のツリー状態 | 145万ノード全展開挿入 | **1件のみ**(ルート、折りたたみ状態) |
| ルート(145万件の配列)を実際に展開 | - | **303ms**、応答維持、5,002件(上限5,000件+「他145万件省略」行) |

小規模JSON(18ノード)での回帰確認も実施し、修正前と同じく全展開されることを確認した(`TVM_GETCOUNT`=18、手動カウントと一致)。
