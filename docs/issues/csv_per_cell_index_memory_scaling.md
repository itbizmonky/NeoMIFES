# Issue: CSVモードの per-cell インデックスが大規模ファイルで大きなメモリを消費する (P1 — 未対応)

- **起票日:** 2026-08-31 (v1出荷判定、10GBファイルでのCSVモード実機検証中に発見)
- **対象:** `src/csvmode/src/csv_model.cpp`(`CsvModel`、`std::vector<CsvCell>`のCSR方式コンテナ)
- **優先度:** P1 (実害はメモリ使用量のみだが、10GB規模でシステムメモリを圧迫しうる実績があるため)
- **対応 Phase:** 未定 (CsvModelの内部データ構造の再設計が必要、要ユーザー確認)
- **関連:** [decode_cache_unbounded_growth.md](decode_cache_unbounded_growth.md) (同じ検証で発見、一時デコードバッファの問題は解消済み、本issueは別の恒常的なメモリコスト)

## 事実

`decode_cache_unbounded_growth.md`の修正(非キャッシュ化+ストリーミング化)適用後、10GBのCSVファイル(5列×約1.4億行、約6.9億セル)を`view.csvGrid.toggle`で開く実機検証を行ったところ、一時デコードバッファによる急激なメモリ膨張(以前は20GB超)は解消されたが、`CsvModel::build()`が構築する**恒常的な** per-cell インデックス自体が徐々に増加し、実行中に開発機のシステム空きメモリが1.2GBまで低下(セーフティ監視スクリプトにより強制終了、危険な状態は回避)。

参考として、同じ検証の1GB CSVファイル(約1330万行)では、グリッド表示自体は正常に動作したが、WorkingSetが8.3GB(元データの約8倍)に達することを確認済み(ストリーミング化以前の測定だが、per-cellインデックス自体の性質は変わらないため同様の傾向が予想される)。

## 推定原因

`CsvModel`は`logmode::LogModel`(1行1エントリ)や`document::LineIndex`(1行1オフセット)と異なり、**セル単位**でインデックスを持つ設計(`std::vector<CsvCell>`のCSR方式コンテナ、WI-16a確定仕様)。`CsvCell`が`startPos`/`endPos`(各`document::TextPos`=`uint64_t`、8バイト×2)を保持するため、1セルあたり最低16バイト+コンテナのオーバーヘッドを要する。10GBファイルで列数が多いほどセル数が増え、行単位のインデックスに比べて本質的にメモリコストが高い構造になっている。

`LineIndex`/`LogModel`のストリーミング化(本コミットで対応)は「デコード時の一時バッファ」問題を解消するものであり、`CsvModel`自体もストリーミング化済み(`csv_model.cpp`の`CsvModel::build()`は`pieceTextStreamed()`を使用)だが、これは一時デコードバッファのピークを抑えるだけで、**構築される`CsvCell`ベクタ自体のサイズ**(セル数に比例)は変わらない。これは設計上必然のトレードオフであり、単純な非キャッシュ化/ストリーミング化では解決しない。

## 影響

- 数百MB〜数GB規模のCSVファイルであれば実用上問題ない(1GBファイルでの実機確認では正常に動作)。
- 10GB規模・多列のCSVファイルでは、per-cellインデックスの構築中にシステムメモリを大きく消費し、開発機のような32GB RAM環境でも危険域に近づきうる。
- 要件定義書は「1000万行のCSVを閲覧・軽編集できる」ことを目標としており(`master_roadmap.md` §10.2)、10GB・億行規模は当初の想定を超える可能性がある。

## 対応方針 (未着手・複数の選択肢を検討)

1. **`CsvCell`のフィールド圧縮。** `startPos`/`endPos`ではなく`startPos`+`length`(`length`を`uint32_t`に縮小可能なら1セルあたり12バイトへ削減)等、既存の`document::Piece`が採用しているのと同様の圧縮を検討。
2. **可視範囲のみの遅延インデックス化。** グリッドUIが実際に表示する行範囲のみをオンデマンドでパースし、`CsvCell`ベクタを全行分事前構築しない設計へ変更(スクロールに応じて再パース)。フィルタ・ソート機能(WI-16d/e)との整合性の検討が必要。
3. **何もしない(現状維持)。** 要件定義書の「1000万行」目標は満たしているため、10GB・億行規模は範囲外として文書化するに留める。

現時点では対応方針を確定せず、ユーザーへ選択肢を提示した上で次フェーズ候補として検討する。
