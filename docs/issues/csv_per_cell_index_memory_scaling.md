# Issue: CSVモードの per-cell インデックスが大規模ファイルで大きなメモリを消費する (P1 — 🟡 部分対応)

- **起票日:** 2026-08-31 (v1出荷判定、10GBファイルでのCSVモード実機検証中に発見)
- **部分対応日:** 2026-09-01 (フィールド圧縮のみユーザー承認のもと実施、10GB規模の根本解消は意図的に対象外)
- **対象:** `src/csvmode/include/neomifes/csvmode/csv_model.h`/`src/csvmode/src/csv_model.cpp`(`CsvModel`、`std::vector<CsvCell>`のCSR方式コンテナ)
- **優先度:** P1 (実害は軽減されたが、10GB規模でのメモリ圧迫リスクは依然として残る)
- **対応 Phase:** 未定 (10GB規模を真に解消するには遅延インデックス化という大規模再設計が必要、今回は対象外と確定)
- **関連:** [decode_cache_unbounded_growth.md](decode_cache_unbounded_growth.md) (同じ検証で発見、一時デコードバッファの問題は解消済み、本issueは別の恒常的なメモリコスト)

## 事実

`decode_cache_unbounded_growth.md`の修正(非キャッシュ化+ストリーミング化)適用後、10GBのCSVファイル(5列×約1.4億行、約6.9億セル)を`view.csvGrid.toggle`で開く実機検証を行ったところ、一時デコードバッファによる急激なメモリ膨張(以前は20GB超)は解消されたが、`CsvModel::build()`が構築する**恒常的な** per-cell インデックス自体が徐々に増加し、実行中に開発機のシステム空きメモリが1.2GBまで低下(セーフティ監視スクリプトにより強制終了、危険な状態は回避)。

参考として、同じ検証の1GB CSVファイル(約1330万行)では、グリッド表示自体は正常に動作したが、WorkingSetが8.3GB(元データの約8倍)に達することを確認済み(ストリーミング化以前の測定だが、per-cellインデックス自体の性質は変わらないため同様の傾向が予想される)。

## 推定原因

`CsvModel`は`logmode::LogModel`(1行1エントリ)や`document::LineIndex`(1行1オフセット)と異なり、**セル単位**でインデックスを持つ設計(`std::vector<CsvCell>`のCSR方式コンテナ、WI-16a確定仕様)。`CsvCell`が`startPos`/`endPos`(各`document::TextPos`=`uint64_t`、8バイト×2)を保持するため、1セルあたり最低16バイト+コンテナのオーバーヘッドを要する。10GBファイルで列数が多いほどセル数が増え、行単位のインデックスに比べて本質的にメモリコストが高い構造になっている。

`LineIndex`/`LogModel`のストリーミング化(本コミットで対応)は「デコード時の一時バッファ」問題を解消するものであり、`CsvModel`自体もストリーミング化済み(`csv_model.cpp`の`CsvModel::build()`は`pieceTextStreamed()`を使用)だが、これは一時デコードバッファのピークを抑えるだけで、**構築される`CsvCell`ベクタ自体のサイズ**(セル数に比例)は変わらない。これは設計上必然のトレードオフであり、単純な非キャッシュ化/ストリーミング化では解決しない。

## 影響

- 数百MB〜数GB規模のCSVファイルであれば実用上問題ない(1GBファイルでの実機確認では正常に動作)。
- 10GB規模・多列のCSVファイルでは、per-cellインデックスの構築中にシステムメモリを大きく消費し、開発機のような32GB RAM環境でも危険域に近づきうる。
- 要件定義書は「1000万行のCSVを閲覧・軽編集できる」ことを目標としており(`master_roadmap.md` §10.2)、10GB・億行規模は当初の想定を超える可能性がある。

## 対応方針・実施内容 (2026-09-01)

着手前に3方針(①フィールド圧縮、②可視範囲のみの遅延インデックス化、③現状維持)を実測値付きで提示した:
- 要件定義書§9の実際の目標は「1000万行のCSVを閲覧・軽編集できる」ことであり(`master_roadmap.md`§10.2)、issueで問題が起きた10GB・約1.4億行はその**約14倍の規模**。目標規模(1000万行×10列と仮定=1億セル)では現行実装(圧縮前24バイト/セル)でも約2.4GBに収まり、実は安全な範囲内だった。
- `sizeof(CsvCell)`は現行24バイト、`endPos`を`length`(`uint32_t`)へ圧縮すると16バイトへ削減できる(MSVCの8バイトアライメントにより`uint16_t`まで縮めても16バイトが下限)。10GB・5列(約7億セル)では24バイト時16.8GB→16バイト時11.2GBで、圧縮だけでは10GB規模の危険を完全には解消しない。
- 遅延インデックス化(②)は真に任意規模でメモリを制御できる唯一の選択肢だが、CSR/span方式の公開APIを全面再設計する必要があり(`CsvGridPane`/フィルタ・ソートへの影響大)、目標規模(1000万行)を超えるケースへの対応のために大きなリスクを取る価値があるか要検討、とした。

**ユーザーが「フィールド圧縮のみ実施(推奨)」を選択。** `CsvCell::endPos`(絶対位置、8バイト)を`CsvCell::length`(`std::uint32_t`、4バイト)+`endPos()`計算メソッドへ置き換え、24→16バイト/セル(33%削減)を達成した。`document::Piece`(`piece.h`)の既存の`static_assert(sizeof(Piece) <= 32, ...)`と同型のガードを`CsvCell`にも追加し、将来の意図しない肥大化を防止した。

**実機再測定(Release、662MB・1330万行・5列のCSV、issueの旧参照測定と同規模):** WorkingSet約1.97GB・Private約1.77GBで安定(セーフティキル不要)。issueの旧参照値(1GBファイルでWorkingSet 8.3GB、ただし`decode_cache_unbounded_growth.md`修正前の測定であり単純比較はできない点に注意)と比べ大幅に改善しているが、**この実測値から10GB・1.4億行規模へ素朴に外挿すると約18GB相当となり、10GB規模の危険自体は依然として残る**(セルベクタ以外のドキュメント/mmapオーバーヘッド等がスケールするため、圧縮の効果はセルベクタ部分の33%削減に限定される)。これはユーザーが承認した通り、10GB規模の根本解消(方針②)を意図的に対象外としたことによる想定通りの残存リスクである。

## 完了条件

- [x] 上記3方針のいずれかを採用するかを決定する(ユーザー確認) — フィールド圧縮のみ採用、遅延インデックス化は対象外と確定
- [x] (方針1採用の場合) `CsvCell`のメモリレイアウトを圧縮し、10GBファイルでの実測メモリを再測定する — 24→16バイト/セルへ圧縮、662MB規模で実測(WorkingSet約1.97GB)。**10GB規模そのものでの再測定は行っていない**(前回同様のリスクを伴う長時間試験のため、662MBスケールでの実測から外挿する形で代替した)
