# Issue: 複数ウィンドウ (要件定義書§6必須機能) が構造的に未実装 (P1 — 🟡 対応中、WI-20a完了・WI-20b残り)

- **起票日:** 2026-09-02 (ユーザーからの品質フィードバック「秀丸/MIFESに到底及ばない」を受けた監査中に発見)
- **対象:** `src/app/main.cpp`(`claimSingleInstance()`)
- **優先度:** P1 (要件定義書§6「必須機能」に明記された項目が完全に未達)
- **対応 Phase:** WI-20a(2026-09-02完了)/WI-20b(残り)、`docs/design/build_plan.md`のWI-20aセクション参照

## 事実

要件定義書§6「必須機能」(編集カテゴリ)は「複数タブ」と並んで「複数ウィンドウ」を明記している。複数タブは実装済みだが、**複数ウィンドウは構造的に不可能になっている。**

`main.cpp`の`wWinMain`は通常起動モードで`claimSingleInstance(singleInstanceMutex)`を呼び、失敗時(既存プロセスが起動中)はプロセス自体の起動を中止する([main.cpp:439](../../src/app/main.cpp)):

```cpp
if (args.mode == LaunchMode::Normal && !claimSingleInstance(singleInstanceMutex)) {
```

つまり、NeoMIFESは「1プロセス=1ウィンドウ」を前提とした設計であり、ユーザーが秀丸/MIFESのように独立したウィンドウを複数開いて並べて作業する(例: 2つのファイルを左右に並べて見比べる、別モニタに別ウィンドウを出す)ことができない。タブは同一ウィンドウ内の切り替えであり、これを代替しない。

## 発見の経緯

ユーザーから「ファイルを閉じるボタンがメニューにない」「右クリックメニューが位置を判別しない」「検索がダイアログでない」という3件の具体的なUI品質バグの報告を受け、調査・修正(WI-18a/WI-18b)を行う過程で、要件定義書§6の必須機能リストと実装状況を照合する監査を実施し発見した。ユーザーへ報告済み、「複数ウィンドウ対応は規模が大きく別Work Itemとすべき」との認識で合意し、今回のWI-18スコープには含めていない。

## 対応方針 (未着手)

シングルインスタンス制約(`claimSingleInstance()`)自体は多くの設計判断(自動保存の重複防止、Git状態の`Workspace`単位キャッシュ等)の前提になっている可能性があり、単純に撤廃するだけでは済まない可能性が高い。少なくとも以下の設計検討が必要:

1. 複数プロセス方式(秀丸/サクラの伝統的な方式) - シングルインスタンス制約を撤廃し、複数の`NeoMIFES.exe`プロセスが独立して起動できるようにする。プロセス間で設定ファイル(`settings.json`等)への同時書き込み競合が発生しうるため、排他制御の設計が必要。
2. 単一プロセス・複数ウィンドウ方式(VSCode等) - `Workspace`を`MainWindow`ごとに複数保持できるようにアーキテクチャを拡張する。既存の「1プロセス=1Workspace」という前提(`Workspace workspace`が`wWinMain`のローカル変数として1つだけ存在)を崩す大規模な変更になる。

いずれの方式を採るかはユーザー判断が必要な設計決定であり、Issue化のみに留める。

**2026-09-02追記(WI-20a着手時):** 当初「複数プロセス方式」で合意しかけたが、実装着手前の調査で`docs/design/basic_design.md` §2.3が既に「単一プロセス内で`MainWindow`を複数インスタンス化(VS Code方式)」を明記し「プロセス分離は起動0.3s要件を満たせないため採用しない」と明確に却下していることが判明。この却下理由(2026-07時点、実装前の推測)は実測起動31.35ms(予算の1/10以下)により実質的に解消されている可能性が高い旨を提示し、設計書通り単一プロセス方式へ差し戻して合意した。
