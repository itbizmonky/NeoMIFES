# Issue: 「100万Undo(24時間ソーク)」が実際にはUndo/Redoを回さないアイドル確認だった (P2 — 未対応)

- **起票日:** 2026-08-31 (v1出荷判定、24時間ソーク実施中にユーザーから「放置していて何の意味があるのか」と指摘を受け発覚)
- **対象:** `.tmp_v1_verify\soak_monitor.ps1`(検証スクリプト、プロジェクト外・gitignore対象)、`docs/design/master_roadmap.md` §12.5チェックリスト
- **優先度:** P2 (100万Undo自体の能力・速度は別途ベンチマークで実測済みのため機能欠陥ではない。テストの検証範囲が計画より狭かったという記録)
- **対応 Phase:** 未定

## 事実

`master_roadmap.md` §12.3(フル版、凍結)の原案には以下の記載がある:

> **Undo ソーク:** 100 万回連続 Undo/Redo を 24 時間

これは「実際に100万回規模のUndo/Redoを連続実行し続けて24時間クラッシュ・メモリ膨張が無いこと」を検証する**能動的なストレステスト**として計画されていた。

しかしv1出荷判定(§12.5軽量版)で実際に実装・実行した`NeoMIFES_V1_SoakTest`(`.tmp_v1_verify\soak_monitor.ps1`)は、NeoMIFES.exeを起動した後は一切操作を行わず、15分おきに「プロセスが生きているか」「WorkingSetのサイズ」を記録するだけの**完全なアイドル放置確認**だった。Undo/Redoは1回も実行されない。

チェックリスト上は「100万Undo(24時間ソーク、メモリ膨張無し)」という項目名のまま、中身が別物(アイドル生存確認)に置き換わっていたことになる。ユーザーからの「放置して不具合が顕在化するとは思えない」という指摘で発覚した。

## 影響

- 「100万回のUndo/Redoを連続実行してもクラッシュ・メモリ膨張しない」という主張自体は、**未検証のまま**である。
- ただし以下の理由で実害は限定的:
  - Undo/Redo自体の性能・正しさは`BM_UndoStack_PushOneMillion`(412.5ms)/`BM_UndoStack_UndoOneMillion`(267.1ms)というgoogle/benchmarkで既に実測済み(瞬間的な処理としては動作する)。
  - `UndoStack`のメモリ無制限成長は別途[`undo_stack_unbounded_memory.md`](undo_stack_unbounded_memory.md)(P2、既存issue)で追跡中であり、本issueが指摘する「ソークで確認できていない」という事実自体は新規だが、その根本的な懸念(メモリ成長)はゼロから見つかったわけではない。
  - 24時間アイドルソーク自体は「何もしなくても劣化しないか」という別の観点で価値があり、これは12時間に短縮の上、継続実施した([`master_roadmap.md`§12.5](../design/master_roadmap.md)「クラッシュ0/メモリ安定性」項目参照)。

## 対応方針 (未着手)

実際にUndo/Redoを連続実行するアクティブなソークスクリプトを新規に書く必要がある。案:
1. `SendInput`等でNeoMIFESへ実際のテキスト入力を送り込み、続けてCtrl+Z/Ctrl+Yを一定間隔で連打するPowerShellスクリプトを新規作成する。
2. あるいは、UI層を経由せず`core::UndoStack`を直接ドライブするヘッドレスなスタンドアロンプローブ(本セッションで使った`lineindex_probe.cpp`/`grep_probe.cpp`と同じ手法)を書き、数時間〜24時間連続でpush/undo/redoを繰り返しWorkingSetを記録する。UI層を経由しないため「実使用」の再現度は低いが、`UndoStack`自体のメモリ挙動検証としては十分な可能性がある。
3. 何もしない(現状維持)。100万Undoの能力自体は達成済みのため、v1の軽量出荷判定としてはこの粒度で十分と判断し、将来の商用配布検討(§12.3フル版)まで先送りする。

現時点では対応方針を確定せず、次フェーズ候補として検討する。
