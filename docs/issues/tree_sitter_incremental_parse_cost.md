- **対象:** [`src/syntax/src/incremental_parser.cpp`](../../src/syntax/src/incremental_parser.cpp) の `IncrementalParser::reparseRange()`

- **関連:** `docs/design/master_roadmap.md` §7.11、Phase 7q/7t の完了記録(いずれも同じDoD未達を記録)、[`gap_analysis.md`](../design/gap_analysis.md) §4.4

> **本項目は Phase 12 直前まで凍結する。** 凍結解除時に判断すべきは「達成する」か「**DoD 値そのものを改訂する**」かの二択であり、後者も正当な結論として認める (達成不能と判明した目標を未達のまま放置し続けるより、正直に改訂する方が健全)。改訂する場合の候補値: 「10万行までは ≤50ms、50万行では ≤200ms」。

## 背景

Phase 7t完了時点で、50万行文書の1文字編集増分再解析が narrow window(可視範囲のみ要求)でも155.95ms・full document(文書全体要求)でも155.45msとほぼ同一という実測が得られていた。この「ウォーク範囲を絞ってもコストが変わらない」という事実から、**ボトルネックは`detail::walkTree()`(ウォーク量に依存)ではなく`ts_parser_parse_string_encoding()`自体にある**、との仮説を立てた。

この関数は文字列ベースAPIであり、呼び出しごとに文書全体のテキストを1つの連続バッファとして事前に用意することを要求する(`SyntaxWorker::workerLoop()`の`BufferSnapshot::extract()`がこれを行う)。tree-sitterはこの制約を回避する**コールバックベースAPI**(`TSInput`+`ts_parser_parse()`)を公式に提供しており、`read(payload, byte_index, position, *bytes_read) -> const char*`という関数ポインタを渡すと、tree-sitterは実際に必要なバイト範囲だけを都度要求してくる。「増分再解析では、編集で無効化されていない大部分の部分木は`old_tree`からそのまま再利用され、その範囲のテキストは一度も`read()`されないはず」という理論に基づき、Phase 7uでこのAPIへの切り替えを実装した。

## 実施内容 (Phase 7u)

- `neomifes::syntax`に`TextChunk`/`TextSourceRead`/`TextSource`(関数ポインタ+payload、`std::function`不使用)を新設し、`reparseRange()`のシグネチャを`std::u16string_view text`から`TextSource source`へ置き換え
- `neomifes::render`に`BufferSnapshotTextSource`(`document::BufferSnapshot`の`pieceView()`を`std::ranges::upper_bound`による二分探索でチャンク単位(`kMaxChunkCodeUnits=4096`コード単位でキャップ)に切り出す実装)を新設
- `SyntaxWorker::workerLoop()`から`BufferSnapshot::extract()`(文書全体materialization)を削除し、`BufferSnapshotTextSource`経由の遅延読み込みへ置き換え
- 単体テスト5件・既存テスト・ベンチマーク一式を新契約に追従させ、Debug/Release/ubsanの870テスト全てgreenを確認

実装自体は正しく完成し、CLAUDE.mdの品質ゲート(ビルド警告0・clang-tidy新規警告0・全テストgreen)を満たしていた。

## 検証結果 — 仮説が誤りだったことが判明

一時的な診断計測(`std::chrono`によるタイミング計測、`read()`呼び出し回数/バイト数カウンタ)を追加し、50万行文書での1文字編集増分再解析を計測した。

**`BufferSnapshotTextSource::read()`の実際の呼び出し状況(narrow window・full document 双方):**

| 項目 | 実測値 |
|---|---|
| `read()`呼び出し回数 | **1回** |
| `read()`で読まれたバイト数 | **8,192バイト** |
| 文書全体のバイト数 | 115,621,560バイト |

→ **遅延読み込みメカニズム自体は設計通り完璧に動作していた**(文書全体のうち0.007%しか読んでいない)。

**にもかかわらず、`ts_parser_parse()`単体のコスト(`ts_tree_edit()`とは別に`std::chrono`で分離計測):**

| 項目 | 実測値 |
|---|---|
| `ts_tree_edit()`(全edits適用) | 0.02〜0.05ms(無視できる) |
| `ts_parser_parse()`本体 | **約300〜325ms** |

**公正な比較のため、Phase 7tが除外していた`BufferSnapshot::extract()`(文書全体実体化)のコストも別途計測した:**

| 項目 | 実測値 |
|---|---|
| `extract()`(50万行文書全体を`std::u16string`へ実体化) | **19.07ms** |
| Phase 7t実測(`ts_parser_parse_string_encoding()`、narrow window、extract()コスト抜き) | 155.95ms |
| Phase 7t実際のエンドツーエンド(`extract()` + `ts_parser_parse_string_encoding()`、公正な合計) | **約175ms** |
| Phase 7u実測(`ts_parser_parse()`、TSInput経由、narrow window) | **約300〜325ms** |

## 結論

1. **文書全体のテキスト事前実体化(`extract()`)は、真のボトルネックではなかった。** そのコストはわずか19msで、旧`ts_parser_parse_string_encoding()`の155msに対して約12%の追加コストに過ぎない。
2. **`ts_parser_parse()`(TSInputコールバックAPI経由)は、`read()`が実際にはごく一部しか呼ばれていないにもかかわらず、旧文字列一括API(`extract()`込みの公正な合計175ms)より約1.8倍遅い(300〜325ms)。** つまりPhase 7uの変更はDoD未達を解消しなかっただけでなく、**明確な性能後退(regression)** だった。
3. 保持木(`old_tree`)を使った増分再解析において、tree-sitterの`ts_parser_parse()`自身の内部処理(木の再利用可否を判定する走査、または増分diffアルゴリズムの一部)が、**実際にテキストを読み直す量とは無関係に、保持木(≒文書)のサイズに比例するコストを持つ**と強く示唆される。この内部コストはコールバックAPI・文字列一括APIのどちらを使っても発生し、後者よりも前者の方がむしろ(関数ポインタ経由の間接呼び出し・チャンク境界管理等のオーバーヘッドで)重くなる。

**対応: Phase 7uの実装は全面的にrevertし、`incremental_parser.h`/`.cpp`・`syntax_worker.cpp`はPhase 7t完了時点のコード(文字列ベース`ts_parser_parse_string_encoding()`)に戻した。** `BufferSnapshotTextSource`関連の新規ファイルも削除。

## 追記 (2026-08-03): 根本原因の特定 + `ts_parser_set_included_ranges()` 実機probe検証 (否定的所見)

「今後の検討候補」の筆頭だった「tree-sitter自身のソースコードを読んで保持木依存コストの正体を特定する」を実施した。

### 根本原因の特定 (vendored tree-sitter source、`build/debug/_deps/tree-sitter-src/lib/src/{parser.c,subtree.c,tree.c,get_changed_ranges.c,stack.c,reusable_node.h}`を直接引用して確認)

`ts_parser_parse()`のメインループ(`parser.c` 2127-2182、`do{ for(version...){ while(active) advance() } } while(version_count!=0)`)は、呼び出しごとに**文書の先頭からEOFまでオートマトンを歩くことが構造的に必須**。個々のステップは`ts_parser__reuse_node()`(`parser.c` 753-836、既知の部分木をO(1)で丸ごと再利用できる)のおかげで軽いが、ステップ**数**自体が「文書サイズ÷平均再利用チャンクサイズ」に比例するため、`TSInput.read()`がほぼ呼ばれなくても(Phase 7uが1回8192バイトしか読まなかったのに300ms超かかった理由の説明がこれで付く)、ループ自体のコストは消えない。`ts_tree_edit()`(`subtree.c` 633-786)自体は編集範囲外を明示的にスキップするO(edit depth)であることも確認済み(実測0.02〜0.05msと整合)。木のバランシング(`ts_parser__balance_subtree()`、`parser.c` 1873-1928)も再利用済み部分木(`ref_count==1`)を明示的にスキップするため無関係。**これはtree-sitterの`ts_parser_parse()`アーキテクチャそのものの構造的限界であり、NeoMIFES側の使い方の誤りではない**と確認できた。

### `ts_parser_set_included_ranges()` 実機probe検証 — 結論: 不採用 (否定的所見)

唯一の未検証の回避策として`ts_parser_set_included_ranges()`(`api.h` 241-267、パーサが実際に読む/歩く範囲を窓に絞りつつ`old_tree`再利用も維持できるAPI)を発見し、実装前に使い捨てprobeプログラム(コミットなし、CLAUDE.mdルール3の規律通り)で以下3点を実機検証した。

**Q1(正しさ): 部分的に成功、しかし実運用で頻発する構文(複数行コメント・生文字列)で致命的に破綻。**

合成C++文書(約338万バイト、namespace包囲+ネストしたif/for+複数メソッドを持つ4000クラス)に対し、全文書解析を基準として、窓(`included_ranges`で絞った、`old_tree=nullptr`のコールド解析)内のトークン分類を比較した:

| 窓の種類 | 結果 |
|---|---|
| クリーンな境界(クラス境界) | ミスマッチ 0/1691 |
| メソッド本体の途中から開始 | ミスマッチ 3/1681(`field_identifier`→`identifier`など軽微、境界近傍のみ) |
| 6段ネストしたifブロックの途中から開始 | ミスマッチ 6/1665(`if`キーワードが`identifier`として誤認識、境界近傍のみ) |
| **複数行`/* */`コメントの途中から開始** | **ミスマッチ 344/343、リーフ数自体が343→1249へ激増** — コメントの残りテキストがコードとして誤解析され(`err=1`のERRORノードも発生)、コメント終了後の実コード(`class`宣言等)まで巻き込んで誤分類が連鎖 |
| **生文字列リテラル(`R"(...)"`)の途中から開始** | **ミスマッチ 341/340、同様の激増** — 文字列内容がコードとして誤解析され、以降の実コードも巻き込まれる |

「窓境界付近だけの軽微なズレ」に留まったのは、構文的にほぼ自己完結した位置(メソッド呼び出しの中、ifブロックの中)から始まる窓のみ。**複数行コメント・生文字列リテラルという、実際のC++ファイルにごく普通に存在する構文の内部から窓が始まった場合、パーサは「コメント/文字列の続きを読んでいる」という字句解析器の内部状態を引き継げず、その内容をコードとして誤って構文解析してしまい、誤分類が窓の広い範囲(時には窓全体)に伝播する。** これはスクロールでランダムな位置に窓が置かれる実運用では稀なケースではなく、ライセンスヘッダやdocコメントを含む多くのファイルで定常的に発生しうる。

**Q2(再利用の実効性): 検証した3シナリオいずれも再利用ゼロ(`reuse=0`)。**

全文書解析(`old_tree`)→1文字編集→窓1で解析(編集位置周辺)→(編集なしで)窓2(窓1と80%重複、近接スクロール想定)→(編集なしで)窓3(文書末尾、Ctrl+End相当の大ジャンプ)、をTSLoggerで`reuse_node`/`cant_reuse_node_*`ログを収集しながら実行した結果:

| 窓 | 所要時間 | `reuse_node` | `cant_reuse_node_contains_different_included_range` | その他の`cant_reuse_node_*` |
|---|---|---|---|---|
| W1(編集直後、編集位置) | 4.93ms | 0 | 0 | 41 |
| W2(近接スクロール、80%重複) | 4.02ms | 0 | 0 | 10 |
| W3(大ジャンプ) | 15.68ms | 0 | 0 | 6 |

**本来もっとも再利用が働くはずの「編集なし・80%重複のスクロール」(W2)ですら、`reuse_node`が1件も観測されなかった。** これは今回の調査を始めた動機である「窓が移動しても重複部分は再利用され続けるはず」という仮説(`ts_parser__has_included_range_difference()`の存在から推測していた)を実測で覆す結果であり、原因(otherDenyの内訳がどの具体的な拒否理由なのか)は本probeの計測粒度では特定できておらず未解明。

**Q3(粗いタイミング): 単体では有望に見えるが、Q1/Q2の失敗により無意味。** W1〜W3はいずれも今回の合成文書における「全文書再解析(old_tree利用、12.56ms)」より高速(4〜16ms)だった。ただしこれは「窓の外を全く読まない/歩かない」ことの直接的な効果であり(根本原因の特定と整合する)、**再利用(`old_tree`の恩恵)によるものではないと考えられる**(Q2でreuse=0だったため)。つまりタイミング面の恩恵自体は本物である可能性が高いが、Q1の致命的な正しさの問題を解決しない限り採用できない。

### 結論

計画(本文書とは別のセッション内plan)で定めた採用基準「(a) 窓中央部の分類が基準と一致 (b) 重複範囲が主に再利用される (c) 明確なタイミング改善」のうち、(a)は複数行コメント/生文字列という頻出構文で明確に不成立、(b)も3シナリオ全てで不成立。**`ts_parser_set_included_ranges()`を単一言語ファイルの任意の行範囲窓(スクロール追従)に適用する設計は不採用と判断し、本番コード(`src/syntax/`・`src/render/`)は一切変更しなかった。** probe(`probe_included_ranges.cpp`)はスクラッチパッド上の使い捨てで、コミットしていない。

50万行文書で約155ms(narrow window)という現状の数値は、tree-sitterの`ts_parser_parse()`アーキテクチャ(文書全体を毎回オートマトンで歩く設計)に由来する実用上の下限に近い可能性が高いと考えられる。

## 今後の検討候補 (未着手、優先度は要再検討)

- **「小さな文脈プレフィックスを窓の前に追加で渡す」緩和策(`ts_parser_set_included_ranges()`の`count>1`機能を使い、`[contextStart, windowStart)`+`[windowStart, windowEnd)`の2レンジを渡す)。** 複数行コメント/文字列の途中から始まる窓の破綻を、直前の何行かをコンテキストとして与えることで緩和できないか、という未検証のアイデア。「どれだけのコンテキストで十分か」自体が任意のネスト深さに対して未解決の問題であり、採用するなら専用のprobeによる別途検証が必要(本investigationでは着手していない)。
- **`ts_tree_edit()`自体は無視できるコスト(0.02〜0.05ms)と確認済みのため、「保持木を使わず毎回ゼロから全文書パースする」設計と実測比較する価値がある。** もし`old_tree`を渡さない完全な再パース(`old_tree=nullptr`)の方が速いとすれば、tree-sitterの増分再解析機能自体がこの利用パターン(巨大文書+単発小編集)には向いていない可能性がある。ただしこれは初回パースと同じO(文書サイズ)コストになるため、根本的な解決にはならない。
- **tree-sitter本体のバージョンアップ**(現行バージョンの内部実装に起因する既知の問題である可能性。上流での修正・改善を追跡する)。
- **「可視範囲のみを含む縮小されたドキュメントコピーに対して独立したパーサインスタンスでフルパースする」設計**(増分再解析自体を諦め、可視範囲外の構文コンテキストを一部犠牲にする代わりにO(可視範囲サイズ)を狙う、ネスト構造の誤判定リスクとのトレードオフを要検討。今回判明した「複数行コメント/文字列の途中から始まる窓は誤爆する」という問題は、このアプローチを採る場合も同様に発生しうる点に注意)。
